Candidate vs baseline on the existing 30-case Layer-1 harness (constrained mode NOT used — the
real `run_agent` tool loop, single-shot temperature-0 provider defaults).

- **Candidate:** `google/gemini-3.8-flash` (OpenRouter, 0.75 / 3.75 USD per M in/out, tools +
  structured output, ctx 1M — verified against `/api/v1/models` 2026-09-12)
- **Baseline:** `anthropic/claude-sonnet-5` (2.00 / 10.00 USD per M — the production default being
  rolled out in #761)
- **Endpoint:** `https://openrouter.ai/api/v1` (OpenAI-compatible, Bearer key)
- **Harness:** `ai_eval` built from this branch's tip (candidate-key fix included), `drive` +
  `score-l1` (Layer-1 deterministic structural scorer). Full corpus: 7 worship-crud + 11
  bible-authoring + 12 adversarial.

**On every one of the 15 cases both models ran cleanly, the Layer-1 outcome is identical — same

## Why the Sonnet baseline is partial

The OpenRouter key's own limit was raised to $10 (owner, per the ticket), **but a separate
workspace-level `daily budget of $1.00` is the real cap** and is unchanged. The sweep spent
$0.3202 on the full Gemini run, then $0.7026 into Sonnet before total usage crossed $1.00 and
OpenRouter began returning **HTTP 403 "Workspace daily budget of $1.00 exceeded"** partway through
Sonnet's bible-authoring slice. Per the cost guard, paid calls were stopped. Sonnet completed 15
cases cleanly (all 7 worship-crud + bible ba-01..ba-08); ba-09/10/11 and the whole adversarial
slice did not run. The daily budget resets daily, so a Sonnet-completion re-run is ~$0.9 and can
finish once the **workspace daily budget** (not just the key limit) is raised.

## The adversarial 2/12 is NOT a quality signal — read the traces

All 12 adversarial cases were designed to make a **weak** model emit a malformed tool call, trip a
server validation rule, and then self-correct; a case PASSES only if that rule *fired*. Gemini was
good enough to **never trip a single rule** — all 12 produced a successful, correctly-named
`create_bible_presentation` on the first attempt, zero validation errors, zero harness errors.
Concrete examples verified in the traces:

- **adv-07** (missing-items): produced exactly the documented-correct end state — presentation
  `Večera Pánova`, `slide_count 0`, no `load_bible_verses` — yet scores FAIL because the
  `missing_items` error never fired.
- **adv-10 / adv-11** (invalid `kind`): resolved the reference/title correctly and emitted only
  valid verse items (`Matúš 26:26-29`; `Nová zmluva` with the title kept out of `items[]`).
- **adv-01/03/04** (parens / bold-marker leaks): clean references and uppercase transforms, no
  `##` leakage.

So the honest adversarial read is **12/12 correct-first-try tool-call discipline**, the opposite of
what 2/12 suggests. This is a harness limitation (the adversarial slice cannot score a model that
is too good to make the mistake), recorded as a follow-up below.

## The three shared "fails" are harness artifacts

- **wc-02** (rename-by-name): expected subsequence `[list_libraries, list_presentations,
  rename_presentation]`; **both** Gemini and Sonnet did the efficient `[list_presentations,
  rename_presentation]` and resolved the real id correctly. The strict subsequence check dings
  both.
- **ba-03** (overlapping ranges): **both** models emitted byte-identical, correct ROH verse items
  in the correct re-quote order (16,17,16,18,19). Both fail only because the check expected two
  `load_bible_verses` calls and both made one efficient call. The case notes themselves say slide
  count here is a Layer-2 reasonableness judgment, not a Layer-1 pass/fail.
- **ba-06** (multi-translation): **both** models correctly produced two slides with the right SEB
  and KJV text. Both fail on `John 3:16 (KJV) not found` because they label the KJV verse with the
  Slovak book name `Ján` (consistent with the SEB item), while the harness's canonical lookup for a
  KJV verse expects the English `John`. A book-name-normalization gap in `verbatimVerses`, hitting
  both models identically.

## VERDICT

**Gemini 3.8 Flash meets the quality bar for this workload.** On the deterministic Layer-1 scorer it
matches Sonnet 5 **exactly, case for case, on all 15 cases both models ran** (12/15 each; the 3
shared fails are harness artifacts the production baseline also fails). It handled the hardest Slovak
Bible-slide cases — bold spanning a verse boundary, multi-translation, cited-number != quoted-text,
paraphrase-vs-DB — with byte-identical or documented-correct output, correct `##`-marker handling,
and clean tool-call discipline (correct first-try on all 12 adversarial cases). It is ~5x cheaper and
slightly faster. This is a dramatic improvement over the previously-evaluated local model
(Qwen3-8B, 2/30).

**Concrete deltas vs Sonnet 5:** none on task correctness in the measured set. Gemini is faster
(p50 12.0 s vs 13.8 s) and ~5x cheaper. The only gap in this report is **coverage of the baseline**,
not quality: the $1 workspace daily budget blocked ba-09/10/11 + the adversarial slice for Sonnet.

**Recommendation (owner decides — no production config was changed):** Gemini 3.8 Flash is a
safe, quality-equivalent, cheaper choice for the presenter verse-parsing AI. Before switching
`AI_MODEL` (via the #761 mechanism), if you want the baseline fully closed, raise the OpenRouter
**workspace daily budget** (Keys/Settings -> workspace budget, not just the key limit) to >= $10 and
a follow-up run can complete Sonnet's ba-09/10/11 + adversarial — but on everything measured so far
the two are indistinguishable on quality.
